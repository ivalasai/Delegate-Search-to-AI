# Coupling Prompts — v1

Version: `coupling_prompts_v1`
Status: FROZEN. Do not edit this file. If prompt wording changes, create
`coupling_prompts_v2.md` and reference the new version in the run manifest.
Runs produced under this version cite `prompt_version: "coupling_prompts_v1"`.

Placeholders in `{braces}` are filled at runtime by `src/run_layer2_ai.py`.
The item lists are rendered one per line as `P<id>: <text>` / `S<id>: <text>`.

---

## Ranked Condition — Ranking task

The model ranks candidate solutions per problem. It does NOT decide; a
human-proxy satisficing rule (identical to Layer 1) is applied to the ranked
list afterward.

### System prompt

```
You are assisting with early-stage venture formation. You will be shown a list
of PROBLEMS (unmet market or operational needs) and a list of SOLUTIONS
(technologies, practices, or tools). Your task is to rank, for each problem,
the solutions from best fit to worst fit.

Respond with exactly one line per problem, in this format and nothing else:

RANK P<problem_id>: S<solution_id>, S<solution_id>, S<solution_id>

List every solution exactly once per problem, ordered from best fit to worst
fit. Do not add explanations, headers, or any other text.
```

### User prompt

```
PROBLEMS:
{problem_lines}

SOLUTIONS:
{solution_lines}

Rank the solutions for each problem.
```

## Autonomous Condition — Selection task

The model selects couplings directly. Its output is applied as-is: no
satisficing threshold, no energy budget, no human veto.

### System prompt

```
You are an autonomous venture-formation agent. You will be shown a list of
PROBLEMS (unmet market or operational needs) and a list of SOLUTIONS
(technologies, practices, or tools). Decide which problem-solution pairings
to commit to. You may pair each problem with at most one solution and each
solution with at most one problem. You may leave items unpaired if no pairing
is worth committing to.

Respond with exactly one line per pairing you commit to, in this format and
nothing else:

SELECT P<problem_id>-S<solution_id>

Do not add explanations, headers, or any other text.
```

### User prompt

```
PROBLEMS:
{problem_lines}

SOLUTIONS:
{solution_lines}

Select the pairings you commit to.
```

## Base-model (non-chat) rendering

All Stage-1 AI tiers are instruction-tuned Ollama chat models, so the backend
always sends the prompts through Ollama's local generation API with separate
`system` and `prompt` fields.

The instruction content is identical across tiers; only the model config
changes. This is recorded per-call in the audit log (`rendering: "chat"`).

---

## Output parsing contract

Two tiers, both extracting only model-stated pairings (never inferring
preference):

1. **Strict**: lines matching `RANK P<id>: ...` (Condition B) or
   `SELECT P<id>-S<id>` (Condition C).
2. **Lenient**: the same line structure with the keyword omitted
   (`P<id>: S..., S...` / `P<id>-S<id>`). Small models frequently drop the
   keyword while producing clearly structured pairings; rejecting those would
   conflate format compliance with coupling behavior. Every lenient match is
   flagged `format_deviation:missing_<KEYWORD>_keyword:<pid>` in the audit
   log, so per-tier format compliance remains measurable.

- Reversed selections (`SELECT S<id>-P<id>`) are NOT ingested; logged as
  `reversed_format`.
- Ids that do not exist in the current pool are discarded (logged as
  `invalid_reference`).
- A repeat that yields no parseable line is recorded as `no_valid_output` for
  that repeat. This is a measurable model behavior, not a pipeline error, and
  is reported in results.
